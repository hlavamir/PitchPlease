# Version 3 — ESP32 + DMX

> Current version: ESP32 receiving DMX512 input and driving 4× WS2811 LED strips. Two physical devices built, with hardcoded DMX start addresses 100 and 200.

## Overview

V3 is a major architecture shift. The microcontroller is now an ESP32 (AZ-Delivery USB-C variant) and the control protocol is DMX512 over RS-485, received via a MAX485 module on a custom PCB. The vvvv patch sends DMX from a computer via a USB-DMX interface (Enttec Pro or Enttec Open). Two identical devices have been built with different hardcoded DMX start addresses.

WiFi and Bluetooth are explicitly disabled in firmware to avoid interference with LED timing.

## Physical Devices

| Device | DMX Start Address |
|---|---|
| Unit 1 | 100 |
| Unit 2 | 200 |

Two more units (3 and 4) are in assembly (DMX addresses TBD) — see [[v3-assembly]] for the internal cable set prepared for them.

## Hardware

- **MCU:** AZDelivery ESP32 NodeMCU Module, CP2102, USB-C, ESP32-WROOM-32 ([Amazon](https://www.amazon.de/-/en/dp/B0D8WB3C22))
- **DMX connectors:** XLR-3 (3-pin)
- **DMX interface:** MAX485 RS-485 transceiver module
- **Level shifter:** POPESQ 74AHCT125N quad bus buffer (on PCB) — shifts ESP32's 3.3V data signals to 5V for the WS2811 strips (one IC, four channels)
- **LED strips:** 4× WS2811 12V, 24 segments per strip (72 LEDs per strip — 3 LEDs per WS2811 IC; 288 LEDs per device total). Adjacent strips are offset by 1/6 of a segment (≈8mm) so their LEDs interleave, reducing hotspots on the frosted tube.
- **PSU:** LXLQZXW 12V 10A 120W AC/DC adapter, 5.5×2.5/2.1mm plug ([Amazon](https://www.amazon.de/-/en/dp/B0C3L7MPY3))
- **PCB:** Custom design in Fritzing, under `v3_esp32_dmx/pcb/`. Original v3 board: `250802_v3-0_esp32_dmx.fzz`, Gerbers in `250805 pcb v3-0/`. Revised **v3.2** board (fixes and full history below): current sketch `260823_v3-2-1_esp32_dmx.fzz`, Gerbers + PCB view SVG in `260823 pcb v3-2-1/`.

## Physical Design

Each device is built around a **130 cm PLEXIGLAS® Satinice tube** (frosted/diffuse, colorless 0D010 DF, Ø60mm outer / Ø54mm inner). The four LED strips are glued to a **12×12mm hollow plastic square profile** (~1m, off-the-shelf from Baumarkt) running through the centre of the tube, one strip per face, so light is emitted in all four directions. The plastic profile has no structural role — it only keeps the LED strips in position. Structure is provided by the 3D printed caps and, in v3.1, the screw rod.

Each end of the tube gets a custom **3D printed cap**. The cap on one end houses all the electronics (PCB, connectors) and the XLR DMX connectors. The other end is a plain closing cap.

**Flash log (2026-10-08).** The ESP32-WROOM-32 has 4 MB flash: two 1.25 MB app slots (the firmware uses ~0.94 MB), a 1.4 MB data partition (unused until now) and 20 KB NVS. The firmware keeps a mini log there (`src/flashlog.cpp`, LittleFS, formatted on the first boot): two files of up to 64 KB, about 90 h of heartbeats each. It survives power-off and firmware updates. Logged: every boot (reset reason, e.g. brownout or crash; build date; DMX address), the first DMX frame, DMX lost for over 2 s and its return, and a heartbeat every 10 minutes (DMX frame rate, redraw rate, `FastLED.show()` and render times). Purpose: the ESP32 may not be powered over USB while the LED supply is on (Espressif: one power source only), so measurements are taken on 12 V and read back later over USB alone with `read-flash-log.command` (port picker; connecting restarts the board, which prints the last 30 lines; then `l` all, `t` last 40, `c` clear). `firmware-flasher.command` asks for the variant: normal, or **refresh measurement** (`-DMEASURE_REFRESH=1`): at every boot it times `FastLED.show()` for 3 s with FastLED's built-in 400 Hz cap (the ESP32 RMT driver's `getMaxRefreshRate`) and 3 s without, logs both, and shows the uncapped rate as a green bar for 5 s (one pixel per 50 Hz). Compiles; not yet run on a unit.

**Gamma.** DMX pixel values are perceptual (equal steps look like equal brightness steps); the firmware multiplies them by the strip and master dimmers and then decodes each channel with `powf(v, 2.2)` to PWM duty. PitchControl therefore sends v3 pixels with gamma 1. Since 2026-10-08 the result is rounded to the LED byte; before, it was truncated, which darkened every value and turned all inputs below 21/255 into 0 (now below 15/255). Compiles (PlatformIO, 2026-10-08); not yet flashed to the units.

## DMX Channel Layout

Per device, starting at the device's DMX start address:

| Channels | Count | Purpose |
|---|---|---|
| +0 | 1 | Master dimmer |
| +1 | 1 | Mode |
| +2 … +5 | 4 | Per-strip dimmers (one per strip) |
| +6 … +77 | 72 | Group A: per-segment RGB (24 segments × 3 channels) |
| +78 … +80 | 3 | Group B |
| **Total** | **81** | channels per device |

## Connection to vvvv

The vvvv patch sends DMX to v3 devices via one of two paths:

- **Direct:** vvvv → Enttec Pro (USB-DMX) → XLR → device
- **Via ArtNet:** vvvv → local ArtNet → QLC+ → Enttec Open (USB-DMX) → XLR → device

Both devices can be addressed simultaneously since they have different start addresses (100 and 200).

The vvvv patch builds each device's frame in `PitchPlsToDMXv3` from four parts. The header bytes `255, 0` (master dimmer, mode) are set in `CreateLightFixtures`. The four strip dimmers `255, 255, 255, 255` are hardcoded in an IOBox inside `PitchPlsToDMXv3`. Then come the 24 × RGB pixel bytes, and no footer. This matches the firmware layout above (verified against `v3-2_esp32_dmx_platformio/src/v3_esp32_dmx.ino`, 2026-10-05). Group B (+78…+80) is never sent, which is harmless because mode 0 assigns no strips to group B. The DMX master byte is always 255; the "D PitchPls v3" macro dims the colours in software instead.

## Deprecated Prototype

`standalone_esp32/` is an earlier prototype that explored a different architecture (audio analysis onboard the ESP32, web-based control UI over WiFi). It is deprecated and may be deleted. ## v3.2 PCB Revision (2026-08-22, updated 2026-08-23 and 2026-08-24)

All three known v3 PCB issues (below) are fixed in the **v3.2** revision. Current sketch: `v3_esp32_dmx/pcb/260823_v3-2-1_esp32_dmx.fzz` (Gerbers + PCB view SVG in `v3_esp32_dmx/pcb/260823 pcb v3-2-1/`). `260822_v3-2-0_esp32_dmx.fzz` (in `260822 pcb v3-2-0/`) is the prior iteration, kept for reference. *(Note: `v3_esp32_dmx/` was reorganized on 2026-08-24 — the old flat `hardware/` folder is now split into `case/`, `firmware/`, and `pcb/`, and files gained explicit version tags, e.g. `v3-0`/`v3-2-0`/`v3-2-1`. Paths below reflect the current layout.)*

- **ESP32 solder holes too small — fixed.** The ESP32 pins are 0.6×0.6mm square; the original custom-part footprint drilled 0.71mm holes (too tight — diagonal of the pin alone is ~0.85mm). Fritzing doesn't support re-importing an edited SVG onto a part already placed in a sketch (edits create a disconnected duplicate part instead), so the fix was applied directly to the part's resource SVG in Fritzing's library (`hlvmr_31b790219a0ccb1c846f3c0357b8f10a_22_pcb.svg`, plus the matching source copy in `v3_esp32_dmx/pcb/fritzing custom parts/esp32_azdelivery_usbc/esp32_azdelivery_usbc_pcb.svg`) with Fritzing closed, then reopened — the already-placed instance picked up the new geometry with no rewiring needed. All 38 pin pads: hole radius `1.6`→`2.16` (SVG pt units), same stroke-width, giving a 1.1mm hole / ~1.95mm pad on the unchanged 2.54mm pitch. The importable `esp32_azdelivery_usbc.fzpz` package (same folder) was left stale after the initial fix and only patched to match on 2026-08-24.
- **MAX485 solder holes too small — fixed.** Same root cause and same 0.6×0.6mm square pins on the MAX485 module footprint (used by both DMX In and DMX Out modules — one shared part definition, so one file edit fixed both placements). Hole radius `1.584`→`2.135`, same 1.1mm hole target. Fixed directly in the library resource SVG (`hlvmr_254a599cd1999c0b730119f1648c1551_12_pcb.svg`) and the repo source copy (`v3_esp32_dmx/pcb/fritzing custom parts/max485_module/max485_module_pcb.svg`). Same stale-`.fzpz` issue and fix as the ESP32 part above.
- **MAX485 leg disconnection (DMX Out module) — fixed, and confirmed correct by field experience.** The GPIO33 → RE/DE trace has been removed in the v3.2 sketch, leaving the DMX-Out MAX485's RE and DE pins floating (unconnected to anything, not tied together). This matches — rather than merely resembles — the physical workaround already proven on both built v3 units: cutting the RE/DE legs of the module (i.e., floating them) is confirmed working in the field. No tie-off (e.g., to VCC) is needed; the current v3.2 routing is the validated-correct end state, not an intermediate one. Standard RS-485 practice says a floating enable pin is undefined, but empirically this specific transceiver module lands in a working transmit-enabled state when floated — worth keeping in mind if a different MAX485 module/breakout is ever substituted, since that assumption may not hold for a different board's default pull state.
- **Onboard step-down unreliable — worked around, then removed.** On 2026-08-22 the STPDWN footprint was left unpopulated (power via the external DC-DC converter, as before) but kept on the layout, along with its two dedicated decoupling caps C1 (12V/GND) and C2 (5V/GND). As of the 2026-08-23 revision, **STPDWN, C1, and C2 have been deleted from the sketch entirely** — confirmed by diffing the sketch's component list, not just visually. Clean removal of genuinely dead circuitry rather than carrying unused footprints forward.

Also as of 2026-08-23: the secondary 12V connection point (previously labeled "12+", same physical part/position) was relabeled **"+12V-"** for clarity, and "+ 5V -" was relabeled **"+5V-"**. Both are cosmetic renames only, confirmed by matching Fritzing's internal modelIndex — same parts, no rewiring.

**Power terminal purposes** (three physical screw terminals, not two — "+ 12V -" and "+12V-" are different physical connectors despite the near-identical name): the **large "+ 12V -" terminal** (`screw_terminal_2_200mil`, wider pitch) on the right edge of the board is the **main power input** — where the external 12V PSU connects. The two smaller terminals at the bottom edge, **"+12V-" and "+5V-"** (`screw_terminal_2_100mil`), are for the **external power module that replaced the onboard STPDWN step-down**: 12V goes out to that module via "+12V-", and the module's regulated 5V comes back onto the board via "+5V-" to power the ESP32/MAX485/buffer logic.

Backups of every original (pre-edit) part SVG/fzpz were initially kept alongside the edited files with a `_backup` suffix, both in the repo and in Fritzing's own library folders. Removed 2026-08-24 once the fix was confirmed working — the pre-fix originals remain recoverable from git history under the old `v3_esp32_dmx/hardware/` path if ever needed.

## v3.2 Circuit Topology (verified from sketch data)

Reconstructed from the actual Fritzing sketch's connectivity data (`.fz` XML extracted from the `.fzz`), not just visual inspection — the PCB view's SVG export turned out to be an unreliable source for this (see Open Questions). Current as of the 2026-08-23 sketch; re-verified against it after the STPDWN/C1/C2 removal (no other nets changed).

**Power:** three rails, everything on the expected one. GND ties ESP32, both MAX485 chips, the SN74AHCT125 (including all four of its OE pins — permanently enabling all four buffer gates, matching the "always-on level shifter" design), both DMX header grounds, and all four LED header ground pins. +5V feeds ESP32, both MAX485 VCCs, and the buffer VCC — sourced from the external power module via the "+5V-" terminal (see below), not generated on-board. +12V feeds all four LED headers' 12V pins directly from the main "+ 12V -" input, and separately from the "+12V-" terminal that feeds the external power module. STPDWN, C1, and C2 are gone as of 2026-08-23 (see above) — no longer part of any rail.

**LED driver path:** `GPIO21→buffer 1A→1Y→R1→LED1`, `GPIO19→2A→2Y→R2→LED2`, `GPIO26→3A→3Y→R3→LED3`, `GPIO27→4A→4Y→R4→LED4`. Each buffer output has its own series resistor before the strip header — **200Ω, 1% metal-film**, confirmed by reading the color bands off all 8 resistors (R1-R4 × 2 devices) on both built/field-tested v3 units, so this is the validated-in-practice value, not a guess. Board silkscreen doesn't print the value, which is why this had been an open question. Cable run from PCB to strip is short (10-15cm), so signal-integrity considerations barely constrain the choice at all — only the first WS2811 IC on each strip sees the raw RC from this resistor and the short cable's parasitic capacitance (each IC reshapes/re-transmits to the next), and at this length even 100Ω vs 470Ω would behave identically; 200Ω sits comfortably in the middle of the general 100-500Ω range used for WS281x data lines regardless. Note: this means GPIO27 (wiki's "Strip 0") physically drives the header silkscreened **LED4**, not LED1 — a labeling mismatch between firmware's "Strip N" naming and the board's header numbers. Not a functional bug, but worth knowing when physically wiring a strip to a header.

**DMX path:** the two MAX485 chips are cross-wired relative to their physical position on the board — the chip sitting near the DMXOUT silkscreen box is actually wired to the DMXIN header, and vice versa. Functionally: ESP32.GPIO16 is a single shared node tied to *both* the DMXIN-side chip's RO (received data) and the DMXOUT-side chip's DI (data to transmit) — a hardware straight-through repeat path, so incoming DMX is visible to firmware and simultaneously pre-wired to retransmit out DMXOUT without shuttling bytes between two UARTs in software. ESP32.GPIO32 drives the DMXIN-side chip's RE+DE (tied together), letting firmware flip that chip between receive and drive on the same shared GPIO16 node — reads like deliberate support for turning the input port around to transmit (RDM-style bidirectional DMX), not an accident. Neither ESP32 hardware UART pin (RXD/TXD) is used for DMX — both stay free for USB/serial-monitor debugging.

**EN reset capacitor:** C5 sits between ESP32.EN and GND — **10µF, 50V electrolytic**, confirmed by physically opening one of the two built devices (not readable from the sketch or silkscreen). Larger than the 100nF-ceramic debounce cap in Espressif's standard auto-reset reference circuit, so this reads as a deliberate longer power-on delay rather than simple debounce — plausibly to make sure the ESP32 doesn't come out of reset before the MAX485/buffer rails or the LED strips' inrush current have settled. Relies on the AZDelivery module's own onboard EN pull-up to form the RC delay; no separate pull-up on this custom PCB.

## Known PCB Issues (pre-v3.2, historical)

- **ESP32 solder holes too small** — see v3.2 fix above.
- **MAX485 leg disconnection (DMX Out module)** — the RE and DE pins of the DMX Out MAX485 module were routed to GPIO33 on the ESP32. The intent was to drive them from firmware, but this couldn't be made to work. With GPIO33 undriven, DE/RE sit LOW — transmitter disabled, no DMX output. Workaround on the v3 board: physically cut the RE and DE legs of the module, i.e. float them — confirmed working on both built units. Fixed for v3.2 (trace removed, pins left floating — the same end state as the leg-cutting workaround, now confirmed as the intended design rather than a stopgap) — see above.
- **Onboard step-down unreliable** — the PCB has a 3-pin footprint for a STPDWN step-down module: DollaTek ADS-5.5V, 4.75V–12V → 5V 800mA. This proved unreliable in practice (ESP32 only stayed powered for a few seconds — likely insufficient current headroom). Workaround: external DC-DC converter — YOURRYONG DE, DC 9V–36V → 5V 5A ([Amazon](https://www.amazon.de/-/en/dp/B0DSJR28JV)). v3.2 initially just left the STPDWN footprint (and its C1/C2 decoupling caps) unpopulated; as of 2026-08-23 all three have been removed from the layout entirely — see above.

## Future Development

### Axis flip mode
Rethink the way mode and per-channel dimmers work. Instead of the current DMX mode/per-strip-dimmer approach, add an **axis flip mode**: take the received 24-pixel brightness curve and resample it at 4 evenly-spaced positions (t = 0, 0.333, 0.666, 1.0 → approximately pixel indices 0, 8, 16, 23). Each of the 4 sampled brightness values drives one of the 4 LED strips as a uniform brightness. This maps the spatial distribution of the audio-reactive signal across strips, rather than addressing LEDs individually.

### 16-bit brightness channel mode (proposal, Miro 2026-10-08)
A second DMX mode: master dimmer, mode, 4 strip dimmers, one RGB colour at full brightness (3 channels), then 24 pixel brightnesses in 16 bits (48 channels): 57 channels instead of 78, so 4 units still fit one universe. It fits PitchControl's model, where all pixels of a fixture share hue and saturation and only the brightness varies per pixel. Caveat: the extra precision only reaches the LEDs if the firmware also dithers (WS2811 takes 8 bits per channel). Logged, not implemented.

### Temporal dithering
The firmware already computes dimmers and gamma in 32-bit float, so the precision exists; it is lost only when the result is written to the 8-bit LED value. Dithering would use the fractional part of that float to alternate between the two nearest LED values over several refreshes (0.3 → the LED shows 1 instead of 0 in about 30 % of refreshes). This is what makes slow fades near black smooth (roughly 2–3 extra bits), with no extra DMX channels. FastLED can dither, but `FastLED.setBrightness(255)` disables it, and it needs refreshes well above the 40 FPS DMX rate (estimated ~200 Hz for 4 × 38 LEDs; not measured). Needs testing on a unit for flicker.

### WiFi bridge
Ability to control lights remotely from a phone. Not a direct phone-to-ESP32 connection — rather a bridge from the phone to vvvv, which then handles the DMX output as usual. See [[wifi-bridge]] for full details.

## Open Questions

- Why does the DMXIN-side MAX485 need GPIO32-controlled RE/DE (turning it into a driver) — is this actually used for RDM, or a leftover from an earlier design intent? Worth confirming against firmware before relying on it.
- Fritzing's flattened PCB-view SVG export is **not reliable for reconstructing which parts are electrically connected** — multi-segment traces don't always share exact endpoint coordinates even where the copper is genuinely continuous, and top/bottom-layer copy of the same footprint can render under different transform chains that make naive position-matching mis-split one physical part into two. The `.fzz` sketch's own `.fz` XML (`<instances><instance><views><pcbView><connectors><connector><connects>`) is the reliable source — but even that mixes in stale breadboard-view connection remnants (filter to `layer` values `copper0`/`copper1`/`copper0trace`/`copper1trace`) and requires manually bridging each `Wire###` instance's own two connector ends, which aren't linked to each other in the data. Worth remembering before trusting any future from-scratch PCB trace analysis on this project.
